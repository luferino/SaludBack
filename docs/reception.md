# Reception access and patient administration (T1–T2)

Reception accounts can read their own active career options and administer patients only within explicitly granted careers. An administrator provisions accounts and grants each career separately; no clinical, assignment, academic-catalog, or general user-management permissions are granted to Reception.

## API contracts

All endpoints require a verified bearer token. Authentication applies only to matched handlers, preserving existing unknown-route responses. Account fields must be strings when present; malformed types, invalid credentials/career codes, and malformed path UUIDs return 400 before persistence. Duplicate usernames or emails return 409; granting an unknown account/career or revoking an unknown grant returns 404. Admin and self operations require a verified UUID actor/subject. Admin mutations also require role `admin` and the indicated enforced permission; checks are performed inside the handler after authentication.

| Method and path | Access | Contract |
|---|---|---|
| `POST /auth/accounts` | Admin + `reception:accounts:write` | Body `{ "username", "password", "email" }`; creates a `reception` user and returns the user JSON without password/audit fields (201). Existing normalization, validation, hashing, and duplicate handling apply. |
| `GET /auth/accounts/:userId/careers` | Admin + `reception:careers:write` | Returns `{ "items": [...] }`, including active and revoked grant periods in grant-time order; an unknown user returns an empty list. |
| `POST /auth/accounts/:userId/careers` | Admin + `reception:careers:write` | Body `{ "career": "kinesiology" | "odontology" }`; creates a separately audited active grant (201). A duplicate active user/career grant returns 409. |
| `POST /auth/career-grants/:grantId/revoke` | Admin + `reception:careers:write` | Revokes a period; repeat requests return the original audit values (200). |
| `GET /reception/careers` | Reception + `reception:careers:read` | Returns `{ "careers": ["kinesiology", "odontology"] }` for the verified subject's active grants only. The database is queried on every request; zero active grants returns an empty array. |

Grant objects are `{ id, user_id, career, granted_by, granted_at, revoked_by, revoked_at }`. Actor and timestamps are server-owned; clients cannot supply them. Career granting verifies the target user has role `reception`. No implicit second-career grant exists.

## Patient administration (T2)

Reception can use only a career explicitly selected on the request and currently granted to the authenticated account. `GET /reception/patients?career=...` lists patients enrolled in that career; `GET /reception/patients/:id?career=...` and `PATCH /reception/patients/:id?career=...` require the same persistent enrollment. `POST /reception/patients/match` accepts `{ career, documento }` and returns only a match boolean and patient reference. `POST /reception/patients/reuse` accepts `{ career, patient_id, documento }`, verifies that exact document/reference pair and enrolls the existing institutional identity without overwriting it. `POST /reception/patients/register` accepts a string or numeric document and string patient fields, then atomically creates the patient and career enrollment using the existing patient validation rules. Patient response DTOs omit audit metadata. Contact updates accept only `email`, `celular`, and `direccion`; identity and birth-date corrections remain admin-owned. Enrollment is independent of subject/group availability. Migration `046_create_reception_patient_enrollments.sql` adds persistent patient-career associations and the narrow Reception permission.

## Revocation serialization contract

For T1, the guarded disposable PostgreSQL integration test verified both career-grant lock orderings. T2 uses `PgReceptionAccessRepository.withActiveCareerScope` for every patient operation: begin a READ COMMITTED transaction, lock and verify the Reception user row, lock and verify its active grant, then lock patient rows. READ COMMITTED rechecks grant eligibility when a concurrent revocation releases the grant lock; scoped callbacks are never replayed. Grant revocation locks/updates the grant row, so a scope check and revocation serialize on that grant; a failed scope check performs no callback and rolls back. Do not introduce global locks or invert the user → grant → patient lock order. The T1 guarded disposable PostgreSQL test verified both lock orderings: a scoped operation holds the grant until commit before revocation completes; a revocation holding the grant first causes the later scoped lookup to reject without invoking its callback. Those 179 integration and 602 unit results apply to the T1 candidate only; they do not verify T2. The T2 candidate separately passed 610/610 unit tests and 180/180 guarded disposable integration tests, including minimal identity reuse, enrollment rollback, duplicate-document registration races, contact serialization across careers, and denial of every patient operation using a pre-revocation signed token. All tests ran without skips, and the disposable database was removed. A six-case differential also preserved existing public-route responses, including successful global patient creation.

The enforced Reception permissions remain limited to `profile:read`, `reception:careers:read`, and `reception:patients:manage`; account provisioning and grant operations are admin-only. Existing global permission guard behavior and `/auth/register` estudiante-only behavior are unchanged. Migration `045_create_reception_access.sql` adds audited grant periods and their active-period uniqueness constraint.
